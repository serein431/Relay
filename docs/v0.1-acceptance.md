# Relay v0.1 验收标准

## 怎么使用这份清单

这是一份发布要求，不是当前完成情况。只有每项有可重复的命令、fixture 或人工操作记录后，才能勾选。界面能打开、能列出会话或 HTTP 返回成功，都不能单独证明分享和接收可用。

v0.1 的目标是 macOS 上的不可变快照：发送方选择 Claude Code 或 ChatGPT 会话，并可附带 Git 工作现场，生成加密包；接收方查看后，有 Git 内容时在新 worktree 中恢复，纯会话包则保存到新的普通文件夹，然后选择一个 Agent 开新会话阅读交接材料。ChatGPT 内部仍使用 `codex` provider、`~/.codex`、`codex://` 和 `com.openai.codex`；Codex CLI 以及 Schema、协议中的技术值继续保留原名。

## A. 构建和安装

- [ ] `pnpm install --frozen-lockfile` 在全新目录成功。
- [ ] `pnpm build` 通过 TypeScript 检查并生成前端产物。
- [ ] `cargo fmt --check --manifest-path src-tauri/Cargo.toml` 通过。
- [ ] `cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings` 通过。
- [ ] `cargo test --manifest-path src-tauri/Cargo.toml` 通过。
- [ ] 在 `adapter/` 中运行 `gofmt` 检查和 `go test ./...` 通过。
- [ ] Tauri debug 应用能启动，且不是依赖浏览器演示数据才能显示内容。
- [ ] macOS 应用包内含签名的 `relay-agent-adapter`，不要求用户另装 Go 或 Agent Capsule。
- [ ] Apple Silicon 实机完成一次完整发送和接收；Intel 构建若未测试，要在下载页明确说明。

## B. Adapter 只读解析

- [ ] `health` 返回 `relay.adapter.v1`、版本、`read_only: true` 和命令列表。
- [ ] `discover_sessions` 能发现 Claude Code 和 `codex` provider fixture，会话按项目和 workspace 正确分组。
- [ ] Claude Code fixture 覆盖普通消息、工具调用/结果、附件引用、辅助目录和 subagent 记录。
- [ ] `codex` provider fixture 覆盖 rollout 消息、工具调用/结果、分支关系和副 Agent 记录。
- [ ] 工具调用保留 `call_id`；结果能指向对应调用。孤立结果和缺失结果会产生 warning。
- [ ] 未知但可见的记录不会消失，会变成 `unsupported` / `unknown`，并把完整度设为 `partial`。
- [ ] provider 内部记录和私有推理只计数，不返回原文。
- [ ] 损坏 JSONL、末尾半行、超大行、超大文件和递归过深数据都有界限，并返回明确错误或 `partial`。
- [ ] 解析前后比较 fixture 目录的文件列表、大小、mtime 和摘要，证明 Adapter 没有写入原生历史。
- [ ] Adapter warning 和 stderr 不含会话正文、token 或完整原始记录。

## C. Handoff 格式

- [ ] [relay-handoff-v1.schema.json](../schemas/relay-handoff-v1.schema.json) 能通过 Draft 2020-12 validator 编译。
- [ ] 最小示例通过验证：

  ```bash
  pnpm dlx ajv-cli@5.0.0 validate \
    --spec=draft2020 \
    --strict=false \
    -s schemas/relay-handoff-v1.schema.json \
    -d schemas/examples/minimal-relay-handoff-v1.json
  ```

- [ ] 将任意块的 `classification` 改为 `provider_internal` 或 `private_reasoning` 后验证失败。
- [ ] 将路径改为绝对路径、`repo://../secret`、含反斜杠或 NUL 后验证失败。
- [ ] 工具调用缺少 `mapping`、`status`、`semantics` 或 `replay_policy: never` 时验证失败。
- [ ] 已包含资产缺少 `byte_length` 或 SHA-256 时验证失败。
- [ ] `unknown` 记录和 `unsupported` 块能保存原类型、安全摘要和映射状态，但不能被标为完整映射。
- [ ] Rust 的运行时 validator 检查 JSON Schema 无法表达的关系：ID 唯一、父记录存在、资产引用存在、`call_id` 成对、行范围合法、统计数量一致。
- [ ] 精选分享使用 `export.mode: selected`，并准确记录省略原因与数量。

## D. Git 只读检查

- [ ] 非 Git 目录、unborn branch、detached HEAD、多个 remote、没有 remote 都有明确结果。
- [ ] staged、unstaged、untracked、rename、delete、二进制改动和文件名中的特殊字符解析正确。
- [ ] merge、rebase、cherry-pick、revert 和 bisect 进行中会阻止代码分享。
- [ ] dirty submodule 会阻止代码分享；Relay 不自动更新 submodule。
- [ ] 仓库有 LFS 规则、但 HEAD、index、工作树和所选相关路径都未命中时，代码分享可以继续。
- [ ] 任一相关路径实际由 LFS 管理时，代码分享会停止；pointer、对象缺失和本机对象完整三种情况都要覆盖，Relay 不自动下载对象。
- [ ] 可疑 ignored 文件只给出本地提示，默认不进入包。
- [ ] 检查命令有超时和输出上限，截断结果不被当作完整状态。
- [ ] Git 检查前后工作树、index、HEAD、refs 和配置均未改变。

## E. 发送和本地预览

- [ ] 会话页显示来源 Agent、项目、workspace、更新时间、消息数和完整度。
- [ ] 用户能逐项取消消息、工具记录、附件、Git staged/unstaged/untracked 内容。
- [ ] 取消任意会话内容后，原生会话文件不会作为隐藏资产进入包。
- [ ] 预览显示远端、分支、HEAD、本地提交、改动文件、附件大小和所有警告。
- [ ] 带凭据的 remote URL 被阻止；保存到包内的 remote 不含 userinfo、query 或 fragment。
- [ ] `.env`、私钥、常见 token 和连接串有警告，用户能回到选择页移除。
- [ ] 会话预览返回稳定的 `preview_sha256`；生成包前重新读取会话，摘要变化时返回 `session_preview_changed`，不开始 Git 捕获，也不创建包。
- [ ] 疑似敏感内容未再次明确确认时不能生成包；后端最终扫描发现新命中项时会撤回确认，错误只含类型、范围和数量，不含命中原文。
- [ ] 用户没有确认时不生成最终包，也不上传任何内容。

## F. Git 捕获和恢复

准备一个 fixture 仓库，含：一个未推送提交、一个 staged 改动、一个 unstaged 改动、一个 untracked 文本文件和一个未选择的 ignored secret。

- [ ] 包含可验证的 Git bundle、staged patch、unstaged patch和选中的 untracked 文件。
- [ ] 接收端先运行 bundle/patch 检查，不在检查前改仓库。
- [ ] 总是在不存在的新目录中创建 worktree，不使用 `--force`。
- [ ] 恢复后 HEAD 与发送方相同。
- [ ] `git diff --cached --binary` 与发送方 staged 内容相同。
- [ ] `git diff --binary` 与发送方 unstaged 内容相同。
- [ ] 选中的 untracked 文件字节、模式和 SHA-256 相同；ignored secret 不存在。
- [ ] 已有分支、已有 worktree 和用户当前工作区没有变化。
- [ ] `git worktree add -b` 成功后的任一步失败都会停止后续写入，并保留失败 worktree 和分支，不自动运行 `git worktree remove` 或强制删分支。
- [ ] 失败响应含 `cleanup_incomplete`、`preserved_worktree_path`、`preserved_branch_ref` 和清理诊断；这些字段指向实际保留的现场。
- [ ] 写入和回退 Git common directory 的 `info/exclude` 时会检查文件身份、内容和权限；检测到外部修改后不覆盖对方内容，并保留 worktree 与分支。
- [ ] 文档明确说明：应用内锁不能约束外部进程，最后一次检查与原子替换之间仍有很短的并发修改窗口，当前实现不作目录句柄级保证。

## G. 加密包、HTTPS 链接和本机分享记录

- [ ] 每个包使用独立随机 256 位密钥和 96 位 nonce，使用 AES-256-GCM 认证加密，固定文件头作为 AAD。
- [ ] 修改密文、AAD、nonce 或 tag 后解密失败，并且没有项目文件被写入。
- [ ] 错误密钥失败，不返回可区分内容的详细错误。
- [ ] 云分享使用规范化的 `https://<relay-host>/s/v1/<share-id>#k=<key>`；本地 `.relaypack` 与密钥也可以分开导入。
- [ ] 服务端只收到 URL fragment 之前的部分；访问日志没有密钥和完整链接。
- [ ] 未安装 Relay 的接收者可以在浏览器中解密分享，查看和搜索完整聊天记录，按对话或工具记录筛选，并复制单条记录。
- [ ] 浏览器接收页可以查看、复制和下载 `HANDOFF.md`，也可以下载原始 `.relaypack`；页面不声称能够恢复 Git 或导入原生聊天历史。
- [ ] 浏览器接收页只允许带随机 nonce 的脚本和样式，并且只能连接同源服务；页面没有第三方 URL、分析代码、WebSocket、`sendBeacon` 或 `XMLHttpRequest`。
- [ ] 缺少密钥、错误密钥、摘要不一致、分享未上传完成、已撤销或过期时，浏览器显示正式的中文说明，不展示密文或内部诊断信息。
- [ ] 页面明确说明托管网页代码理论上可以读取 fragment；包含私有代码或账号信息时建议使用桌面应用。
- [ ] 对象 ID、每条分享自己的上传令牌、撤销令牌和解密密钥彼此独立，均来自安全随机源。
- [ ] 默认过期和手动撤销实际生效；撤销后旧链接不能再次下载密文。
- [ ] 界面明确写出“拥有完整链接的人都能读取”，不把 fragment 描述成身份认证。
- [ ] 客户端与服务端都拒绝超过 32 MiB 的密文，并完成接近上限的真实上传和下载测试；明文、payload 合计、单文件和 untracked 数量限制也有边界测试。
- [ ] 桌面端用 JSON `POST /v1/shares` 预留分享；R2 在预留阶段没有密文，公开下载不能读取未完成分享。
- [ ] 收到上传令牌和撤销令牌后，桌面端先把包路径、长度、摘要和两种令牌写成 `pending_upload`，并完成文件与目录同步，之后才发 PUT。
- [ ] 公开 PUT 先触发没有正文的 Durable Object `authorize`；Worker 把请求正文直接流式写入 R2，再触发没有正文的 `complete`，Durable Object 用 R2 `HEAD` 核对长度与摘要。
- [ ] 服务端完成状态为 `ready` 后，本机记录原子改为 `active` 并删除上传令牌；撤销令牌仍可用。
- [ ] `pending_upload` 会出现在分享记录页。包存在且长度、摘要未变时可以继续上传；包丢失或改变时不能上传，仍可撤销。
- [ ] upload deadline 到达后，Durable Object alarm 会清理未完成预留和可能已经写入的 R2 对象；R2 删除失败时会重试。
- [ ] 旧版 direct POST 只作为兼容接口存在；新版桌面端不会自动退回。
- [ ] 分享历史目录和文件权限仅限当前用户，锁文件拒绝 symlink，并用 `flock` 保护多进程读写。
- [ ] `.record.*.tmp` 的完整记录可恢复，损坏记录会隔离，冲突记录不会覆盖现有文件，仍被其他进程锁定的活动文件会跳过。
- [ ] macOS 上分享历史目录的 Time Machine 排除属性写入后会回读验证。

厂商网页分享链接不属于 Relay 包协议。没有稳定解析器和 Git 现场时，不能把 `claude.ai` 或未知 ChatGPT 网页链接写成完整交接；这些入口目前均未实现，不能写成已经支持。

## H. 恶意包

以下 fixture 必须在写 worktree 前被拒绝：

- [ ] 绝对路径、`../`、反斜杠混淆、NUL、Windows 盘符和 UNC 路径。
- [ ] symlink、hardlink、设备文件、FIFO 和 socket。
- [ ] 重复路径、大小写冲突和 Unicode 规范化冲突。
- [ ] 压缩炸弹、伪造展开大小、文件数过多和单文件超限。
- [ ] 资产 SHA-256 不符、缺少资产、重复 ID 和悬空 `asset_ref`。
- [ ] 指向未知 `tool_call` 的结果、循环父关系和无效分支关系。
- [ ] patch 试图修改 `.git`，或 untracked 文件的父目录是 symlink。
- [ ] 需要外部 Git filter、含任何相关 LFS 管理路径或 dirty submodule 的包。

拒绝后检查目标仓库和原工作区无变化，临时明文目录已经清理。

## I. 开始继续开发

- [ ] 恢复成功后生成 `HANDOFF.md` 和结构化材料，内容包含目标、当前状态、下一步、测试结果和重要文件。
- [ ] 用户可选择“用 Claude Code 继续”或“用 ChatGPT 继续”。
- [ ] Relay 使用参数数组启动 Agent，不经过 shell，也不拼接分享链接中的命令。
- [ ] 含 Git 内容时，新会话工作目录是新 worktree，只额外读取 Relay 交接目录；纯会话包使用新建的普通文件夹，根目录只包含交接文件。
- [ ] 首条提示只要求阅读交接材料并继续，不要求运行安装、构建、测试或历史工具调用。
- [ ] Claude Code 启动前后运行 `claude agents --json --all --cwd <worktree>`；只有唯一的新 background 会话 ID、匹配目录和合理开始时间都成立时才返回 `VERIFIED`。
- [ ] Claude Code 的 `working`、`blocked`、`done`、`failed`、`stopped` 或未知状态能原样映射为不会误导用户的结果；`blocked` 没有等待原因时仍有通用提示。
- [ ] ChatGPT 先使用不含 worktree 路径或提示的 `codex://` probe URL 枚举全部 macOS 处理应用；没有通过验签的候选时，不构造也不打开带本机路径的 deep link。
- [ ] ChatGPT 候选应用通过固定的 OpenAI bundle ID `com.openai.codex`、Team ID、所有架构和嵌套代码检查后，Relay 才明确指定该应用打开 `codex://new?path=...&prompt=...`。
- [ ] ChatGPT 成功结果为 `OPEN_REQUESTED`，界面只说明请求已交给通过验证的 ChatGPT 应用，不声称任务已经创建或提示已经发送。
- [ ] `~/.claude` 和 `~/.codex` 中原有会话文件没有被修改。
- [ ] 未安装目标 Agent 时给出清楚提示，不自动安装。

## J. 人工使用检查

- [ ] 一位没有参与发送的人，仅看接收预览就能说清项目、当前任务、已完成工作和下一步。
- [ ] 接收者在新会话中能继续做一处小改动并运行他自己选择的测试。
- [ ] 发送者取消一个敏感工具结果后，接收端全文搜索确认它不在 Handoff、资产或日志中。
- [ ] 中途关闭应用后，原工作区不变；临时目录下次启动能识别并清理。
- [ ] 分享和接收界面能区分“会话可分享但代码被阻止”和“全部可分享”。

## v0.1 不承诺

以下情况不作为首版通过条件：写入原生 Agent 历史、实时共同编辑、Windows/Linux 客户端、自动运行项目命令、自动更新 submodule、自动下载 LFS、在同一个已有工作区继续、导入 Claude 或 ChatGPT 厂商网页分享链接。
